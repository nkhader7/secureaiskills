      Security Skill Requirements From Standards And Research

      Build Requirements

      1. Explicit security objective State the threat class, target assets, expected evidence, non-goals, assumptions, and user-facing outcome. A skill that cannot name what it detects and what it intentionally ignores is not ready for scanning. Scanner check: objective, scope, and non-goals are present.
      2. Structured, versioned contract Require stable id, name, trigger, description, version, owner, changelog, supported formats, input schema, rule schema, output schema, and deprecation policy. Scanner check: missing or unstable contract fields fail authoring quality.
      3. Rule-to-standard mapping Map every rule to CWE, OWASP ASVS, OWASP Top 10, LLM Top 10, NIST SSDF practice, cloud benchmark, or CVSS factor where applicable. Keep mappings machine-readable. Scanner check: each rule has at least one source or standard reference.
      4. Deterministic rule model Separate rule identity, pattern, parser, evidence extractor, confidence logic, severity logic, remediation, and suppression conditions. Avoid rules that rely only on free-form prose. Scanner check: rules have IDs, severity, evidence, remediation, and deterministic matching notes.
      5. Input and target boundaries Define accepted file types, maximum file size, binary handling, generated files, ignored paths, symlink policy, archive handling, dependency manifests, and network access rules. Scanner check: target selection cannot silently scan unrelated or sensitive paths.
      6. Output contract Emit stable JSON or table fields for rule ID, title, severity, confidence, evidence, file, line, data classification, remediation, standard mapping, trace ID, and no-findings state. Scanner check: output is parseable, complete, and redacts unsafe evidence.
      7. Human-readable authoring Use Markdown with structured frontmatter for primary authoring, YAML for rule catalogs, JSON for generated indexes, and TOML only where simple configuration is more readable. Scanner check: chosen format matches audience, complexity, and validation needs.
      8. Remediation quality Every finding needs concrete fix guidance, safe examples, unsafe examples, verification steps, and rollback or compensating-control notes when direct remediation is not possible. Scanner check: remediation is actionable and does not introduce weaker controls.

      Security Scanner Requirements

      9. Skill supply-chain integrity Skills must declare source, author, review status, checksum, signature or trusted provenance, dependency list, and allowed tool capabilities. Treat third-party skills as untrusted code. Scanner check: missing provenance, mutable remote references, or unpinned dependencies are flagged.
      10. Prompt-injection resilience Target files, tool output, comments, markdown, commits, and issue text can contain hostile instructions. Skills must separate instructions from evidence and ignore target-file commands. Scanner check: skill explicitly rejects instruction following from scanned content.
      11. Secret handling and redaction Never print full credentials, private keys, tokens, session IDs, cookies, or PII. Use deterministic masking, safe snippets, hash-only comparison, and explicit retention rules. Scanner check: evidence templates cannot leak raw secrets.
      12. Tool and network containment Declare whether tools may run commands, read files, write files, call networks, install dependencies, or execute code. Default to read-only, offline, and workspace-scoped behavior. Scanner check: dangerous tools require explicit allowlist and user approval.
      13. Command safety Ban destructive commands, shell injection patterns, unquoted paths, curl-to-shell installs, broad recursive deletion, credential export, and command construction from untrusted text. Scanner check: skill examples and runbooks are scanned like source code.
      14. Data minimization Only collect files and fields needed for the detection task. Do not upload repositories, logs, dependency graphs, or findings to external services unless explicitly configured. Scanner check: external API usage and telemetry destinations are declared.
      15. Parser hardening Handle malformed YAML, TOML, JSON, XML, Markdown, archives, encodings, huge files, nested structures, entity expansion, and parser errors without crashing or trusting content. Scanner check: parser failure mode is safe and observable.
      16. XML and deserialization safety Disable external entities, remote DTDs, schema fetches, unsafe object deserialization, templating side effects, and custom loader execution in every format parser. Scanner check: format examples do not require unsafe parser features.

      Detection Quality Requirements

      17. Complete test oracle Every skill needs true positives, false positives, false negatives, true negatives, and Critical/High/Medium/Low/Info cases. Include tiny, normal, and large project fixtures. Scanner check: all case types and severities are represented.
      18. Severity calibration Severity must consider evidence strength, exploitability, reachability, impact, environment, privileges, compensating controls, confidence, and CVSS-style reasoning. Scanner check: severity is justified, not hardcoded only by regex.
      19. False-positive controls Define suppressions for examples, docs, tests, generated code, placeholders, deny-all policies, local-only endpoints, and verified safe compensating controls. Scanner check: suppressions require reason, scope, and expiration where useful.
      20. False-negative probes Include obfuscation, split strings, environment indirection, multi-file flows, base64-like values, generated code, nested config, and framework-specific variants. Scanner check: hidden-risk probes exist for every high-risk rule family.
      21. Evidence chain Findings must show why the rule fired, what context was considered, which files were correlated, and what assumptions remain unresolved. Scanner check: no finding should be an unsupported label.
      22. Confidence model Use confidence separate from severity. Low confidence high-impact findings should route to review instead of being dropped or overstated. Scanner check: findings include confidence and review-needed state.
      23. Benchmark metrics Track precision, recall, F1, time-to-first finding, parse time, scan time, package size, memory pressure, context tokens, and stable output conformance. Scanner check: changes update benchmark baselines.
      24. Regression and mutation tests Run fixtures on every change, mutate vulnerable examples, verify suppressions, and test malformed inputs. Add a regression case for every bug found in the skill. Scanner check: no release without passing fixture and mutation tests.

      LLM And Agent Requirements

      25. Role and instruction hierarchy Define system, developer, skill, user, tool, and target-content boundaries. The skill must not allow target files to override scanner policy. Scanner check: instruction hierarchy is explicit.
      26. Context assembly limits Specify chunking, summarization, deduplication, source attribution, maximum tokens, sensitive-file exclusion, and how evidence is selected for LLM reasoning. Scanner check: context cannot accidentally include unrelated secrets.
      27. Tool-use policy Separate planning from execution. Require dry-run previews for risky actions, read-only defaults, deterministic arguments, and no tool calls derived directly from untrusted content. Scanner check: skill has a tool allowlist and escalation rules.
      28. Hallucination controls Findings must cite exact evidence. If evidence is absent, emit no finding or needs-review. Never invent file paths, line numbers, dependencies, versions, CVEs, or standards mappings. Scanner check: report schema requires evidence source fields.
      29. Adversarial content handling Test with files that ask the model to ignore rules, reveal secrets, disable scanners, claim false safety, or output malformed JSON. The skill must stay policy-bound. Scanner check: adversarial fixtures are included in the test project.
      30. Safe LLM API configuration API endpoint, client ID, and secret fields must be optional, masked, never persisted in cleartext, never included in downloads, and scoped to simulation or approved live testing only. Scanner check: credential fields are write-only or redacted in artifacts.

      Operations, Governance, And Release Gates

      31. Observability and auditability Emit parse, load, context, plan, execute, correlate, suppress, report, and export spans with duration, inputs, rule counts, target counts, finding counts, and errors. Scanner check: trace plan exists and has stable span names.
      32. Error handling Malformed config, missing files, parser errors, timeout, permission denial, and partial scans must produce clear degraded results rather than silent success. Scanner check: failure modes are documented and tested.
      33. Review and approval workflow Require owner review, security review, test evidence, source citations, benchmark delta, backwards-compatibility note, and release notes for every skill change. Scanner check: metadata includes review status and last audited date.
      34. Vulnerability handling Define how to report skill defects, false negatives, unsafe examples, prompt-injection bypasses, secret leaks, and dependency vulnerabilities in the skill package. Scanner check: security contact and disclosure process exist.
      35. Compatibility and portability Declare supported engines, model assumptions, operating systems, path formats, encoding expectations, browser-only behavior, offline behavior, and version constraints. Scanner check: skill can degrade gracefully outside the ideal runtime.
      36. Release gate A skill is releasable only when contract validation, security scan, prompt-injection tests, fixture tests, benchmark thresholds, redaction checks, and documentation checks pass. Scanner check: release status is computed from objective gates, not manual optimism.
